# 对话逻辑与场景扩展

## 产品约束

对话自由，任务用于后台识别经历和学习证据。用户可以聊天、求助、拒绝、提前回答、改变主意；教学目标不能覆盖用户真实选择。图片、人物和可用物品是固定事实，模型不能凭空补充。

## 共用流程

`识别后的原话 + 实际问题 + 当前场景事实 → SceneDialogue.evaluate → 场景规则校验 → 程序提交事实 → 播音与下一幕`

- 正常回答、步骤衔接时的回答、服务端本地识别使用同一个 `evaluate`。
- 结果统一为 `decision / conversation / help / clarify / unresolved`。只有确定的 `decision` 可以改变事实。
- 过期、重复的结果归为 `ignored`，不会播音、重新提问或写入学习记录。
- 已能在本地确定的输入不额外等待语义服务。未解决的候选由原有 DeepSeek 服务理解，实时人物负责回答用户。
- `semanticSpec` 从场景配置生成目标、可选值、当前事实和限制。服务端不再维护一份咖啡/早餐选项清单。
- 模型只返回候选意思；`validateCandidate` 重新经过场景规则，不接受模型提供的 `world`、`complete` 等结果。浏览器收到候选后再按当前世界版本校验。
- `isCurrentTurn` 统一检查练习、场景、步骤、消息修订及阶段，防止旧回复改动新状态。

## 场景负责什么

`scene-dialogue.js` 的场景适配器声明：

| 配置 | 用途 |
| --- | --- |
| `tasks` | 场景任务、实际问题、可选值及显示文案 |
| `worldKey` | 当前事实在应用状态中的位置 |
| `fields` | 事实变化对应的学习项 |
| `facts / constraints` | 已确认事实、物品范围、不可虚构的内容 |
| `evaluate(input)` | 预览当轮意思，返回统一结果，不修改页面或原世界 |
| `validateCandidate(input, candidate)` | 按相同事实规则验证模型候选 |

咖啡继续由 `coffee.js` 管理订单、错单、留杯和完成条件；早餐由 `breakfast.js` 管理选饮料、递杯、添加饮料的前置条件。不同动作不强行共用一个状态机。机场、办公室的任务声明已集中在适配器中，页面直接读取，避免问题文案出现两份。

`app.js` 和 `breakfast-ui.js` 仍负责把已验证的结果提交到对应场景、刷新图片、记录学习证据、播放声音。音频生命周期由原有 voice runtime 管理。

## 新增场景的步骤

1. 声明实际存在的人物、物品、可改变的事实和完成条件。
2. 编写一个小的场景规则模块，预览/应用合法状态变化；保持输入不变，必要时带版本号和事件去重。
3. 在共享入口注册适配器。无需再分别为“正常回答、过渡期回答、后台识别”添加场景判断。
4. 接入场景图片、UI 展示、NPC 背景及实际提交逻辑；这部分仍属于新场景制作，不是单靠配置就会自动生成。
5. 按同一套行为回归：选择、改口、提前回答、实际问题下的 yes/no、聊天提到物品、求助、不可用物品、重复/迟到反馈、任务完成后继续聊天。

`scene-dialogue.test.js` 中的酒店适配器是隔离的扩展验证，不是已上线的酒店场景。

## 本次边界

这是一轮共享入口和校验协议的重构，保留现有场景行为、响应节奏与小任务粒度存档。没有新增英语水平分级，也没有重写整个语音系统。

现有场景的短句解析仍然保留；复杂表达依赖语义理解。本次没有将语义返回值升级为任意多字段计划，咖啡的多字段选择目前仍由其本地规则处理。后续应围绕“意图是否识别正确、事实是否能合法改变”扩展规则，不再在页面事件中添加某一句话的特判。
